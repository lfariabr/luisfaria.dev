# LinkedIn Post — AWS Cloud Architecture for a Delivery Startup

Amazon Web Services (AWS) offers 200+ services. My Masters assignment asked me to pick the right ones for a company that cut IT start-up costs by 80% after moving to the cloud.

This term I'm studying Cloud Computing Fundamentals and Assessment 1 was a design challenge: propose a secure, scalable cloud architecture for ABC Enterprises, a delivery and payments fictional startup that absorbed a 10x customer surge in a single month without adding headcount.

No recipe given. Just requirements and a blank canvas.

I went with AWS. Partly because they already had Route 53 in their existing setup, and partly because the breadth of managed services made it straightforward to justify every architectural decision in the brief.

Here's how I broke down the stack:
1. Route 53: DNS layer, the front door to everything
2. Elastic Load Balancer (ELB): distributes traffic and runs health checks before requests hit compute
3. EC2 + Auto Scaling: horizontally scalable compute with resource pooling; handles traffic spikes without manual intervention
4. S3: object storage for assets, backups, and static content; practically unlimited and cheap
5. RDS: managed relational database, removing the operational overhead of running own DB server
6. Lambda: serverless compute for event-driven flows like order confirmations and payment notifications; fast, zero idle cost

The biggest insight wasn't the services themselves - it was understanding why layer them this way. Security lives at every level: IAM least-privilege, MFA enforcement, encryption at rest and in transit, security groups on EC2. A cascade of decisions from DNS down to the database, not a single switch.

Studying for a Masters while working means assignments like this don't stay abstract for long. The same patterns show up in the systems I work with every week.

Building in public, sharing the architecture diagrams, the reasoning, and yes, the assignments too.
