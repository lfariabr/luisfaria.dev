## Layer 1: Health Check Endpoints

Three tiers of health check, each with a different audience:

| Endpoint | Audience | HTTP Status | Payload |
|----------|----------|-------------|---------|
| `GET /health` | Load balancer / liveness probe | Always `200` | `{ "status": "ok" }` |
| `GET /health/ready` | **Pulsetic / uptime monitors** (public) | `200` when healthy, **`503` when degraded** | Coarse check statuses only — no latencies, no system info |
| `GET /health/details` | CI pipeline / on-server tooling (**IP-whitelisted**) | `200` when healthy, **`503` when degraded** | Full checks with latencies + system diagnostics |

### Behavior When a Dependency Fails

When MongoDB or Redis is down, **both** `/health/ready` and `/health/details` return **HTTP 503** with `"status": "degraded"`. This is intentional:

- **Pulsetic** should be configured to treat `503` as "degraded" (not "site down"), and trigger an alert only after 2+ consecutive failures to avoid false positives during deploys.
- **CI pipeline** uses `/health/details` from inside the Docker network and rolls back if it gets a non-200.

### `/health/ready` Response (public — minimal)

```json
{
  "status": "ok",
  "timestamp": "2026-02-12T10:00:00.000Z",
  "checks": {
    "mongodb": { "status": "ok" },
    "redis": { "status": "ok" }
  }
}
```

When degraded (HTTP 503):

```json
{
  "status": "degraded",
  "timestamp": "2026-02-12T10:00:00.000Z",
  "checks": {
    "mongodb": { "status": "error" },
    "redis": { "status": "ok" }
  }
}
```

### `/health/details` Response (internal — IP-whitelisted)

Only accessible from trusted sources (loopback, Docker bridge, `10.x` private networks).
Returns `403 Forbidden` for all other IPs.

```json
{
  "status": "ok",
  "timestamp": "2026-02-12T10:00:00.000Z",
  "checks": {
    "mongodb": { "status": "ok", "latency": "3ms" },
    "redis": { "status": "ok", "latency": "1ms" }
  },
  "system": {
    "memoryUsage": "45%",
    "loadAvg1m": "0.12",
    "loadAvg5m": "0.08",
    "cpus": 1,
    "processUptime": "2h 30m",
    "nodeVersion": "v20.x.x"
  }
}
```

### Files

- `backend/src/routes/health.ts` — route definitions + `isTrusted()` IP guard
- Mounted in `backend/src/index.ts` via `app.use(healthRoutes)`

## Layer 2: Error Tracking (Sentry)

### Backend (`@sentry/node`)

- **Instrumentation**: `backend/src/instrument.ts` — imported first in `index.ts`
- **GraphQL errors**: Apollo plugin captures non-auth errors via `Sentry.captureException()`
- **Express errors**: `Sentry.setupExpressErrorHandler(app)` catches unhandled Express errors
- **Filtered out**: `UNAUTHENTICATED`, `FORBIDDEN`, `BAD_USER_INPUT` (auth flow, not bugs)
- **Performance**: 20% trace sampling in production
- **`beforeSend` filter**: Checks `event.contexts?.response?.status_code` for HTTP 401/403 (typed Sentry `ResponseContext` field). Uses `hint.originalException` to inspect the raw thrown error — if it's a `GraphQLError` whose `extensions.code` matches `UNAUTHENTICATED`, `FORBIDDEN`, or `BAD_USER_INPUT`, the event is dropped.

### Frontend (`@sentry/nextjs`)

- **Instrumentation file**: `frontend/src/instrumentation.ts` — **required for Next.js 13+** to initialize Sentry on server/edge runtimes
- **Config files** (project root):
  - `sentry.client.config.ts` — browser-side error capture + session replay
  - `sentry.server.config.ts` — SSR error capture
  - `sentry.edge.config.ts` — edge middleware error capture
- **Next.js config**: `next.config.ts` wrapped with `withSentryConfig()`
- **Global error page**: `src/app/global-error.tsx` — catches React rendering errors
- **Filtered out**: `ResizeObserver` noise
- **Session replay**: 1% of sessions, 100% of errored sessions

### Environment Variables

| Variable | Where | Description |
|----------|-------|-------------|
| `SENTRY_DSN` | Backend `.env` + Docker Compose | Backend Sentry DSN |
| `NEXT_PUBLIC_SENTRY_DSN` | Frontend `.env` + Docker Compose | Frontend Sentry DSN (public, client-side) |

### Setup Steps

1. Go to [sentry.io](https://sentry.io) → Create free account
2. Create **two projects**: one for Node.js (backend), one for Next.js (frontend)
3. Copy the DSN from each project
4. Set `SENTRY_DSN` and `NEXT_PUBLIC_SENTRY_DSN` in:
   - Root `.env` (for local dev)
   - GitHub Secrets (for CI/CD — passed to Docker Compose on the server)
   - Server `.env` at `/var/www/portfolio/.env`
5. Redeploy — Sentry will start capturing errors immediately

### Sentry Free Tier Limits

- 5,000 errors/month
- 10,000 performance transactions/month
- 50 session replays/month
- More than sufficient for a portfolio site

## Layer 3: Uptime Monitoring (Pulsetic / Better Stack)

### What It Does

External service pings `https://luisfaria.dev/health/ready` every 60 seconds from multiple global locations. Alerts via Discord + email when:
- Site is unreachable (HTTP timeout)
- Health check returns non-200 for 2+ consecutive checks (degraded state)
- SSL certificate is expiring

### Important: 503 = Degraded, Not Down

`/health/ready` returns **HTTP 503** when a dependency (MongoDB/Redis) fails. Configure your uptime monitor to:
- Treat 503 as "degraded" — not a full outage
- Require **2+ consecutive failures** before alerting (avoids false alarms during rolling deploys)
- The response body always includes `"status": "degraded"` so you can parse it if needed

### Setup Steps (Pulsetic)

1. Go to [pulsetic.com](https://pulsetic.com) → Create free account
2. Add monitor: `https://luisfaria.dev/health/ready`
   - Check interval: 60 seconds
   - Regions: Sydney + US East (cover your server region + global)
   - Expected status: 200
   - Confirmation period: 2 checks (avoid false positives on deploy restarts)
3. Add notification channel: Discord webhook
4. Optional: Create a public status page at `status.luisfaria.dev`

### Alternative: Better Stack

1. Go to [betterstack.com](https://betterstack.com) → Create free account
2. Add heartbeat monitor: same URL and settings
3. Connect Discord integration

### No code changes needed — this is purely an external service configuration.

## Layer 4: Resource Alerts (Cron Script)

### What It Monitors

| Resource | Threshold | Frequency | Alert Channel |
|----------|-----------|-----------|---------------|
| CPU load (1m avg) | > 85% of cores | Every 5 min | Discord webhook |
| Memory usage | > 85% | Every 5 min | Discord webhook |
| Disk usage (root `/`) | > 85% | Every 5 min | Discord webhook |
| Docker containers | Any expected container down | Every 5 min | Discord webhook |

### Alert Deduplication

Repeated alerts for the same check are suppressed for **30 minutes** (6 consecutive runs). State files are stored in `/var/lib/monitor/`. This prevents Discord spam when a threshold stays exceeded.

### Security Model

| Concern | Solution |
|---------|----------|
| Script runs as | Dedicated `monitor` system user (not root) |
| Docker access | `monitor` added to `docker` group (read-only socket) |
| Webhook secret | Stored in `/etc/monitor/monitor.env` (chmod 600, owned by `monitor`) |
| Log rotation | Logrotate config rotates daily, keeps 7 days, compresses |

### Script Location

- Source: `server/monitor-resources.sh`
- Logrotate: `server/monitor-logrotate.conf`
- Server: `/opt/monitor/monitor-resources.sh`

### Server Setup

```bash
# 1. Create dedicated monitor user (no login, no home)
useradd --system --no-create-home --shell /usr/sbin/nologin monitor
usermod -aG docker monitor

# 2. Deploy script
mkdir -p /opt/monitor
scp server/monitor-resources.sh root@serverIp:/opt/monitor/
chown -R monitor:monitor /opt/monitor
chmod 750 /opt/monitor/monitor-resources.sh

# 3. Restricted secrets file
mkdir -p /etc/monitor
cat > /etc/monitor/monitor.env <<'EOF'
DISCORD_WEBHOOK_URL=https://discord.com/api/webhooks/YOUR_WEBHOOK
EOF
chown monitor:monitor /etc/monitor/monitor.env
chmod 600 /etc/monitor/monitor.env

# 4. State directory for alert deduplication
mkdir -p /var/lib/monitor
chown monitor:monitor /var/lib/monitor

# 5. Cron (every 5 minutes, runs as monitor user)
cat > /etc/cron.d/monitor-resources <<'EOF'
*/5 * * * * monitor /opt/monitor/monitor-resources.sh >> /var/log/monitor-resources.log 2>&1
EOF

# 6. Logrotate
scp server/monitor-logrotate.conf root@serverIp:/etc/logrotate.d/monitor-resources

# 7. Create log file with correct ownership
touch /var/log/monitor-resources.log
chown monitor:monitor /var/log/monitor-resources.log

# 8. Test
sudo -u monitor /opt/monitor/monitor-resources.sh
```

### Log Location

- `/var/log/monitor-resources.log` on the server (rotated daily, 7 days retention)

## CI/CD Integration

### Post-Deploy Health Check

The GitHub Actions deploy pipeline (`ci.yml`) uses the internal `/health/details` endpoint (accessible from Docker network):

```yaml
# Backend deep health check (verifies MongoDB + Redis connectivity)
# Uses /health/details (IP-whitelisted, trusted from Docker network)
HEALTH_RESPONSE=$(docker exec nginx_gateway curl -sf "http://backend_api:4000/health/details")
if echo "$HEALTH_RESPONSE" | grep -q '"status":"ok"'; then
  echo "✅ Backend deep health check passed"
fi
```

If the health check fails, the pipeline automatically rolls back to the previous commit.

### Sentry — What You Should See on the Dashboard

For each captured error, Sentry shows:
- **Issue title**: the error message
- **Stack trace**: full call stack with source-mapped file names + line numbers
- **Tags**: `service: portfolio-api`, `environment: development/production`
- **Breadcrumbs**: recent events leading up to the error (HTTP requests, console logs)
- **Session replay** (frontend only): video-like recording of user actions before the crash

### Sentry — What Gets Filtered (NOT sent)

The `beforeSend` filter silently drops these — you will NOT see them on the dashboard:
- HTTP 401/403 responses (auth flow)
- GraphQL errors with codes: `UNAUTHENTICATED`, `FORBIDDEN`, `BAD_USER_INPUT`
- Frontend `ResizeObserver` errors (browser noise)

To verify filtering works: trigger a 401 by calling a protected query without auth — check Sentry and confirm no event appears.

## Troubleshooting

### Frontend Sentry Not Capturing Errors

**Symptom**: Backend errors appear in Sentry, but frontend errors don't.

**Common Causes**:
1. **Missing `instrumentation.ts`** (most common) — Next.js 13+ requires `frontend/src/instrumentation.ts` to initialize Sentry
   - Solution: Create the file with:
     ```typescript
     export async function register() {
       if (process.env.NEXT_RUNTIME === 'nodejs') {
         await import('../sentry.server.config');
       }
       if (process.env.NEXT_RUNTIME === 'edge') {
         await import('../sentry.edge.config');
       }
     }
     ```

2. **Missing `NEXT_PUBLIC_SENTRY_DSN`** — Environment variable not set or not available at build time
   - Solution: Add to `.env`, `.env.production`, and Docker Compose
   - Rebuild the frontend after setting the variable

3. **Sentry configs not initializing** — Check browser console for Sentry-related errors
   - Solution: Verify DSN is valid, configs have correct syntax

4. **Source maps not uploading** — Errors appear but with minified stack traces
   - Solution: Set `SENTRY_AUTH_TOKEN` environment variable for builds
   - Generate token at sentry.io → Settings → Auth Tokens

### Backend Sentry Not Working

**Symptom**: No backend errors appearing in Sentry.

**Common Causes**:
1. **`instrument.ts` not imported first** — Must be the very first import in `index.ts`
2. **Invalid DSN** — Check `SENTRY_DSN` environment variable
3. **Errors being filtered** — Check `beforeSend` function isn't dropping legitimate errors

## Learning: SRE Basics

| Concept | Implementation |
|---------|---------------|
| **Liveness probe** | `GET /health` — "is the process running?" (always 200) |
| **Readiness probe** | `GET /health/ready` — "can the process serve traffic?" (200 or 503) |
| **Internal diagnostics** | `GET /health/details` — full system info, IP-whitelisted |
| **Error budget** | Sentry free tier = 5K errors/month (if you exceed this, something is very wrong) |
| **Incident detection** | Pulsetic detects outages in < 2 min |
| **Incident response** | Discord alerts + Sentry stack traces = fast diagnosis |
| **Resource monitoring** | Proactive alerts every 5 min prevent OOM kills and disk-full crashes |
| **Alert fatigue** | 30-min dedup cooldown prevents Discord spam |
| **Least privilege** | Monitor script runs as dedicated `monitor` user, not root |
| **Secret management** | Webhook URL in restricted `/etc/monitor/monitor.env` (chmod 600) |
| **Graceful degradation** | Health check returns 503 with `"degraded"` when a dependency is down |
| **Observability pillars** | Logs (Winston) + Metrics (health/cron) + Traces (Sentry) |
