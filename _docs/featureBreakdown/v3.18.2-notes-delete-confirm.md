# v3.18.2 — Confirm Before Deleting a Note

## GitHub Issue

**Issue:** [#297](https://github.com/lfariabr/luisfaria.dev/issues/297)

**Title:** `My Notes: confirm before deleting a note`

**Summary:**
Delete fired the mutation on the first tap. On mobile, Edit and Delete sit side by side at the bottom of every card, so one mis-tap permanently removed a note.

## Acceptance Criteria

- [x] Delete never fires without an explicit confirmation
- [x] Dialog names the note being deleted
- [x] Cancel leaves the note untouched
- [x] Confirm deletes, shows progress, and closes the dialog
- [x] Tests cover confirm and cancel paths

---

## Overview

A confirmation dialog in front of the only destructive action in My Notes.

## Problem

`NoteCard`'s Delete button called `onDelete(note.id)`, which `page.tsx` wired straight to the `deleteNote` mutation. There was no confirmation and no undo, and the backend hard-deletes.

## Changes

- `page.tsx` keeps a `pendingDelete: Note | null`. The card's Delete only sets it.
- A `Dialog` (existing primitive, no new dependency) shows *Delete this note? "Weekly update 05/10/2026" will be permanently removed. This can't be undone.* with **Cancel** / **Delete note**.
- `confirmDelete` runs the mutation:
  - success → close the dialog, refetch;
  - mutation returns `false` → keep the dialog open, `toast.error`, log a warning;
  - while in flight → both buttons disabled, label `Deleting...`, and the dialog can't be dismissed.

**Rejected alternative:** an undo toast. It means deferring the mutation for a few seconds, and the delete is silently lost if the user navigates away during that window.

|------|--------|
| `frontend/src/app/notes/page.tsx` | `pendingDelete` state, `confirmDelete`, confirmation dialog |
| `frontend/src/__tests__/app/NotesPage.test.tsx` | Confirm, cancel and failure tests replace the one-tap delete test |
