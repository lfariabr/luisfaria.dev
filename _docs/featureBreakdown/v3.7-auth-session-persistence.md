# v3.7 — Auth Session Persistence

## GitHub Issue

**Issue:** [#235](https://github.com/lfariabr/luisfaria.dev/issues/235)

**Title:** `fix(auth): stabilize session persistence — refresh intermittently logs users out`

**Description:**
Logging in, then refreshing a protected page (`/admin`, `/notes`) **sometimes** redirects back to `/login` as if the session is gone. Authorization works; authentication/session *persistence* is unstable. This issue tracks making session restore resilient and removing the cookie-scope footguns.

**Acceptance criteria:**
- [x] Hard-refresh `/admin` and `/notes` repeatedly on apex and www → zero spurious logouts
- [x] A real expired/invalid token still cleanly redirects to `/login`
- [x] A simulated transient ME failure does **not** log the user out
- [x] Backend refuses to boot with a `JWT_SECRET` < 32 chars
- [x] Frontend + backend test suites green

---

## Overview

Makes the client session-restore path resilient so a refresh only logs you out when you are *actually* unauthenticated. Replaces the all-or-nothing `ME` bootstrap with an explicit auth `status` state machine, scopes the auth cookie to a single canonical host, relaxes `sameSite` to `lax`, and fails fast on a weak JWT secret.

## Problem

Production is **single-origin** (nginx serves `luisfaria.dev/` and `/graphql` from the same droplet), so this was never a cross-site-cookie problem. The flakiness was client-side:

- **`AuthContext` treated any `ME` failure as "logged out."** `onError: () => setUser(null)` fired identically for a real `401/UNAUTHENTICATED` and a transient network/5xx blip. Protected pages redirected the instant `isAuthenticated` flipped false → any hiccup on refresh = bounced to `/login`.
- **www-vs-apex cookie desync.** The cookie is host-only; nginx answers on both hosts, so a login on one wasn't sent on the other.
- **`sameSite: 'strict'`** withheld the cookie on top-level navigation into `/admin` (bookmark / external link) → middleware bounced an already-logged-in user.
- **No `JWT_SECRET` strength guard** — a weak/rotated secret silently invalidates every token (mass logout).

## Changes

### 1. `frontend/src/lib/auth/AuthContext.tsx` (core fix)
- Added an explicit `AuthStatus = 'initializing' | 'authenticated' | 'unauthenticated' | 'error'` exposed on the context.
- Auth state is now **derived from the query result** (works for refetches), not one-shot `onCompleted`/`onError` callbacks.
- `isUnauthenticatedError()` classifies failures: only a real `UNAUTHENTICATED` GraphQL code or a `401` is a logout. An established session is preserved through a blip; a **first-boot (refresh) transient failure enters the recoverable `error` state — never `unauthenticated`** — so a valid cookie + a network blip shows a retry affordance instead of bouncing to `/login` (and never an infinite spinner).
- Added an `online` listener that re-verifies the session when connectivity returns (self-heal).
- `refetchUser()` returns an awaitable `Promise<void>`; `login`/`register`/`logout` set `status` explicitly.

### 2. `frontend/src/components/auth/SessionRetry.tsx` (new)
- Small shared component shown on protected routes when `status === 'error'`: a message + Retry button (calls `refetchUser`). Used by both the admin layout and the notes page.

### 3. `frontend/src/app/admin/AdminLayoutClient.tsx`, `frontend/src/app/notes/page.tsx`
- Redirect to `/login` **only** when `status === 'unauthenticated'` — never during `initializing` or `error`. `error` renders `SessionRetry`; render gates use `status === 'authenticated'`.
- Admin login redirect now preserves the exact path (`/login?redirect=<encoded pathname>`) so nested routes like `/admin/users` return correctly after login (matches the middleware behavior).

### 4. `backend/src/utils/authUtils.ts`
- Auth cookie `sameSite: 'strict'` → `'lax'` so the cookie survives top-level navigation into protected routes (keeps CSRF protection for cross-site POSTs). `COOKIE_DOMAIN` support left intact but unused by default (the nginx redirect makes a host-only cookie sufficient).

### 5. `backend/src/config/config.ts`
- Fail-fast at boot if `JWT_SECRET` is < 32 chars (skipped under tests). Missing-secret was already caught by the required-env check.

### 6. nginx `www` → apex 301 (server-local, **not committed**)
`server/nginx/default.conf` is gitignored and managed on the droplet. Apply this on the server so every request lands on the apex host (one origin owns the cookie):

```nginx
# Port 80: force HTTPS + apex in one hop
location / {
    return 301 https://luisfaria.dev$request_uri;
}

# New 443 block: https://www → https://apex (reuses the same cert)
server {
    listen 443 ssl;
    server_name www.luisfaria.dev;
    ssl_certificate     /etc/letsencrypt/live/luisfaria.dev/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/luisfaria.dev/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    return 301 https://luisfaria.dev$request_uri;
}

# Main 443 block: scope to apex only
server_name luisfaria.dev;
```

Apply with `docker compose exec nginx nginx -t && docker compose exec nginx nginx -s reload`.

## Deployment notes

- Ensure `JWT_SECRET` on the droplet is **≥ 32 chars** — the backend now refuses to boot otherwise. If it must change, note that rotating it logs out existing sessions once.
- Apply the nginx `www`→apex change and reload nginx.
