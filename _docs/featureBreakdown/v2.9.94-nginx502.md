# v2.9.94 Incident Breakdown — nginx 502 / Production Outage

## Overview

Site went down with a **502 Bad Gateway** on 2026-03-10 at ~07:56 UTC.
Total downtime: ~12 hours (including sleep 😅).
Root cause: a chain reaction started by a security patch that silently broke the Next.js build.

---

## The 5 Problems

---

### Problem 1 — 502 Bad Gateway on nginx

**What you saw:** `502 Bad Gateway — nginx/1.29.5`

**What was happening:**
nginx (`nginx_gateway`) proxies all web traffic to the `frontend_app` container. When nginx starts, it resolves the hostnames of its upstream services. If `frontend_app` is not running, DNS resolution fails and nginx refuses to start — it exits with:
```
host not found in upstream "frontend_app"
```
Both containers were stuck in a restart loop, each waiting on the other.

**Source:** nginx depends on `frontend_app` being healthy at startup. Since `frontend_app` was crash-looping, nginx could never get past its own boot sequence.

---

### Problem 2 — `frontend_app` crash loop: `Cannot find module '/app/server.js'`

**What you saw on `docker logs frontend_app`:**
```
Error: Cannot find module '/app/server.js'
```

**What was happening:**
The Next.js Docker image uses `output: 'standalone'` in `next.config.ts`. This tells Next.js to produce a self-contained `server.js` file inside `.next/standalone/` that the container runs directly. If the build doesn't produce it, the container starts, immediately crashes, and Docker restarts it forever.

The build was completing without errors — but `server.js` was never generated, because `next.config.ts` itself was failing to load (see Problem 5).

**Source:** `frontend/Dockerfile` runs `CMD ["node", "server.js"]` — if the build didn't produce it, every start is a guaranteed crash.

---

### Problem 3 — `turbopack.root` pointed to `/` inside Docker

**What you saw (locally):** Turbopack workspace root warning in dev mode.

**What happened in the Stripe feature PR (`f098099`):**
`next.config.ts` had this added to silence a Turbopack dev warning:
```ts
turbopack: {
  root: path.resolve(__dirname, '..'),
}
```
Locally, `__dirname` is something like `/Users/you/project/frontend`, so `..` resolves to the project root — harmless.

Inside Docker, `WORKDIR` is `/app`, so `__dirname` is `/app` and `path.resolve('/app', '..')` resolves to `/` (the filesystem root). This could cause Next.js to treat the entire server filesystem as the workspace root during build, contributing to the standalone output being misrouted to a `frontend/` subdirectory instead of the expected root path.

**Fix:** Removed `turbopack.root` entirely. It was only suppressing a dev-mode warning and had no value in production builds.

---

### Problem 4 — SEO audit was blocking deploys (the deadlock)

**What happened:**
The CI/CD pipeline had this dependency chain:
```
tests → build-check → seo-audit → docker-build → deploy
```
The SEO audit script works by fetching live pages from `https://luisfaria.dev`. When the site is down, every fetch fails, the audit scores 0%, and the job exits with code 1 — **blocking the Docker build and deploy jobs from running**.

This created a perfect deadlock:
- Site is down → SEO audit fails → Docker image not built → site stays down

**Fix:** Two changes to `.github/workflows/ci.yml`:
1. Removed `seo-audit` from `docker-build`'s `needs` list — deploys now gate only on tests passing, not SEO
2. Added `continue-on-error: true` to `seo-audit` — it still runs and reports, but a failure never blocks anything

```yaml
# Before
docker-build:
  needs: [backend-test, frontend-test, seo-audit]  # ❌ seo-audit could deadlock deploy

# After
docker-build:
  needs: [backend-test, frontend-test]              # ✅ tests are the only gate
```

---

### Problem 5 — Static Sentry import crashed `next.config.ts` at load time

**This is the root cause of everything.**

**What happened:**
Commit `04eab55` (the security fix for `serialize-javascript`) added this to `frontend/package.json`:
```json
"overrides": {
  "serialize-javascript": "7.0.3"
}
```
`serialize-javascript` is a transitive dependency of `@sentry/nextjs`. Forcing version 7.0.3 broke the internal module resolution of `@sentry/nextjs`.

`next.config.ts` had a **static top-level import**:
```ts
import { withSentryConfig } from '@sentry/nextjs';
```
When Node loads a `.ts` config file, it evaluates all top-level imports first — before any conditional logic runs. Because `@sentry/nextjs` was broken, this import threw an error. Next.js caught it silently, fell back to **default configuration** (no `output: 'standalone'`), and continued the build as if nothing was wrong.

The build "succeeded" — but produced no `server.js`. Every subsequent Docker push deployed a broken image.

**What made it hard to debug:**
- `npm run build` exits 0 (success)
- No error is printed — Next.js silently ignores a broken config file
- The breakage only manifests at container start, minutes later on the server
- GitHub Actions GHA layer cache kept serving the broken image even after fixes

**Fix:** Removed `withSentryConfig` from `next.config.ts` entirely.

```ts
// Before — static import at module load time, crashes if @sentry/nextjs is broken
import { withSentryConfig } from '@sentry/nextjs';
export default sentryEnabled ? withSentryConfig(nextConfig, {...}) : nextConfig;

// After — clean, no Sentry wrapper
export default nextConfig;
```

Sentry still works at runtime — it initialises via `sentry.client.config.ts`, `sentry.server.config.ts`, and `sentry.edge.config.ts`. The `withSentryConfig` wrapper was only adding build-time optimisations (source map uploads, tree-shaking debug code), and it was never running in Docker builds anyway since `NEXT_PUBLIC_SENTRY_DSN` is not passed as a build arg in CI.

**Added guard to `frontend/Dockerfile`** to catch this regression immediately on future builds:
```dockerfile
RUN test -f .next/standalone/server.js || \
    (echo "ERROR: Next.js standalone build failed - server.js not found" && exit 1)
```
If `server.js` isn't there, the Docker build itself fails — instead of silently pushing a broken image.

## Summary of Changes

| File | Change |
|---|---|
| `frontend/next.config.ts` | Removed static `import { withSentryConfig }` and the Sentry wrapper entirely |
| `frontend/Dockerfile` | Added `test -f .next/standalone/server.js` guard after `npm run build` |
| `.github/workflows/ci.yml` | Removed `seo-audit` from `docker-build` needs; added `continue-on-error: true` to `seo-audit` |

## Key Takeaways

1. **Silent build failures are the worst kind.** A config file that crashes at load time but lets the build "succeed" is extremely hard to debug. Always add explicit assertions after critical build steps.

2. **npm overrides can have non-obvious transitive effects.** Forcing a dependency version is sometimes necessary for security, but always check what packages depend on it first.

3. **Circular dependencies in CI pipelines are a production risk.** Any step that requires the live site to be healthy should never be on the critical path of deploying to the live site.

4. **Docker layer cache can mask fixes.** GHA cached a broken build layer and kept serving it even after code changes. When debugging Docker issues, check whether cached layers are being reused (`CACHED` in build logs).

5. **Container names ≠ Compose service names.** `container_name: frontend_app` vs `services.webapp` — running `docker compose up -d --force-recreate frontend_app` fails silently. Always use the service name (`webapp`).
