## Overview

Rate limiting gets its own vocabulary, a recorded decision, and a standard that describes where the code is going rather than where it was.

## Problem

1. **Three ways to call the limiter** (`middleware/rateLimiter.ts`, `utils/applyRateLimit.ts`, direct `rateLimiter.limit`) across seven call sites, with errors built by hand at each.
2. **Numbers in two places.** Chatbot and APOD share `RATE_LIMIT_*` from config; Goggins, register and health write literals. Chatbot was documented as 5/hour, `.env.example` said 10/hour, and the code default was 5/minute.
3. **Three `RateLimitInfo` shapes**, two of them conflicting GraphQL types.
4. **Fail-open everywhere**, including the features that spend OpenAI and Resend money.
5. **The v3.22.3 standard described that state as the contract**: per-call-site `rateLimiter.limit`, `<feature>:<subject>` keys with no IP subject, "a silent limit is a bug", and `TOO_MANY_REQUESTS` while every client checks `RATE_LIMITED`.

## Changes

### 1. `CONTEXT.md`
New "Rate limiting" section: **Rate limit**, **Subject**, **Window**, **Visible rate limit**, **Silent rate limit**, **Fail open / Fail closed**, each with `_Lives in_: backend/src/rateLimiting/`.

### 2. `docs/adr/0001-rate-limiting-domain.md` (new, first ADR)
One module owning a named list of Rate limits behind `consume(name, subject)`; domain errors mapped at the edge; visibility and failure mode per rate limit; `rl:<rateLimit>:<subjectKind>:<id>` keys. Rejected: per-call-site `rateLimiter.limit`, fail open everywhere, every limit visible, `TOO_MANY_REQUESTS`, skipping on a missing Subject.

### 3. `CODING_STANDARDS.md`
"Rate limiting" rewritten for `consume`, IP as a Subject, and Silent rate limits. "Errors" says `RATE_LIMITED` via `Errors.rateLimited`.
