# v3.21.1 — Record Payments via Stripe Webhook

## GitHub Issue

**Issue:** [#313](https://github.com/lfariabr/luisfaria.dev/issues/313) (part of epic [#311](https://github.com/lfariabr/luisfaria.dev/issues/311); blocks [#314](https://github.com/lfariabr/luisfaria.dev/issues/314))

**Title:** `feat(support): record Payments via Stripe webhook (v3.21.1)`

**Summary:**
Today the site only knows a Payment happened if Luis checks the Stripe dashboard. There is no webhook, no Payment record, and the only Discord signal is a client-side "checkout initiated" ping sent before the Supporter has paid. This ticket records every Payment from Stripe's own events, notifies Luis server-side when money actually lands, thanks coffee Supporters by email, and lists Payments at `/admin/payments`.

## Acceptance Criteria

- [ ] Requests with a missing or invalid Stripe signature are rejected with 400 and write nothing
- [ ] `checkout.session.completed` with `payment_status=paid` creates a paid Payment; unpaid creates a pending one
- [ ] `async_payment_succeeded` / `async_payment_failed` move a Payment to paid / failed
- [ ] `charge.refunded` moves the matching Payment to refunded
- [ ] Replaying the same event does not create a second Payment, a second Discord ping, or a second email
- [ ] Discord ping is sent server-side on paid; the client-side "checkout initiated" ping is gone
- [ ] Coffee Supporters get the thank-you email from `contact@luisfaria.dev`; meeting Supporters do not
- [ ] `/admin/payments` lists Payments for ADMIN only; the GraphQL query is denied to other roles and anonymous users
- [ ] Stale TODOs removed from `stripe.ts`
- [ ] Backend tests: signature rejection, each event handler, idempotency, admin query auth. Frontend test: admin list

## Overview

Second of three Support checkout tickets. A signed Stripe webhook becomes the source of truth for Payments: the site stores each one, pings Discord when it is paid, emails coffee Supporters a thank-you, and shows a read-only list in the admin area. It also builds the email layout that v3.21.2 reuses for the meeting booking email.

## Problem

1. **No record of Payments.** `backend/src/services/stripe.ts` creates checkout sessions and reads their status, but nothing is stored. The only history is the Stripe dashboard.
2. **Discord says "initiated", not "paid".** `StripeDialog.tsx` sends `💰 Stripe checkout initiated` from the browser before payment, so abandoned checkouts look like money.
3. **No thank-you.** A Supporter who buys a coffee hears nothing back from the site.
4. **Webhook secret unused.** `config.stripeWebhookSecret` exists and `.env.example` marks it "reserved for Phase 2".
5. **Stale TODOs** (`// TODO: integrate with Discord`, `// TODO: test assertion`) in `stripe.ts`.

## Changes

### 1. `backend/src/routes/stripeWebhook.ts` (new)
`POST /webhooks/stripe` using `express.raw({ type: 'application/json' })`. Verifies `stripe-signature` with `stripe.webhooks.constructEvent(rawBody, sig, config.stripeWebhookSecret)`; any failure returns 400 and touches nothing. Dispatches on event type:

| Event | Effect |
|---|---|
| `checkout.session.completed` | Upsert Payment by session id. `paid` if `payment_status=paid`, otherwise `pending` |
| `checkout.session.async_payment_succeeded` | Payment → `paid` |
| `checkout.session.async_payment_failed` | Payment → `failed` |
| `charge.refunded` | Find Payment by payment intent id → `refunded` |
| anything else | 200, ignored |

Returns 200 quickly once the Payment write succeeds; email and Discord failures are logged, not surfaced as 5xx (otherwise Stripe retries and the write path re-runs).

**Idempotency.** Payment has a unique index on the Stripe session id, and writes are upserts. Side effects (Discord ping, email) fire only on the transition into `paid`, using an atomic `findOneAndUpdate` filtered on `status: { $ne: 'paid' }`, so replays and duplicate deliveries do nothing.

> **Note:** If tracking processed event ids turns out to be needed (e.g. for `charge.refunded` replays), add a `processedEventIds` field or a small collection. Status-transition guards should cover the four events above without it.

### 2. `backend/src/index.ts`
Mount the webhook router **before** the global `app.use(express.json())` at line 138, so the raw body reaches signature verification. `healthRoutes` (line 141) is unchanged.

### 3. `backend/src/models/Payment.ts` (new)
Fields: `email` (Supporter email from Stripe `customer_details.email`), `productKey` (`coffee` | `meeting`, from session metadata), `amount` (minor units), `currency`, `status` (`pending` | `paid` | `failed` | `refunded`), `stripeSessionId` (unique), `stripePaymentIntentId` (indexed), timestamps. Not linked to `User`.

### 4. Server-side Discord ping
New backend helper (proposed `backend/src/services/discord.ts`) posting to `DISCORD_WEBHOOK_URL`. On transition to paid: `💰 paid AUD 5 — coffee`.

> **Note:** The backend has no Discord helper today and `DISCORD_WEBHOOK_URL` is not in `backend/src/config/config.ts`. Add it to config and `.env.example`.

### 5. Email: reusable layout + coffee thank-you
- Reusable layout (proposed `backend/src/services/emailLayout.ts`): card layout modelled on the Goggins email, in stone/emerald, taking a heading, body and optional CTA button. v3.21.2 reuses it.
- `backend/src/services/resendMailer.ts`: add a coffee thank-you sender. From `contact@luisfaria.dev`, reply-to `contact@luisfaria.dev`. Sent by the webhook on transition to paid when `productKey=coffee`. Meeting Supporters get no email here; v3.21.2 sends them the booking email with thanks inside it.

### 6. `frontend/src/components/stripe/StripeDialog.tsx`
Remove the client-side `💰 Stripe checkout initiated` ping. Keep the "FAB opened" ping in `StripeFab.tsx`.

> **Note:** `StripeDialog.tsx` also sends `💳 Stripe option selected: <productKey>`. Not covered by the design session; keep it unless Luis decides otherwise.

### 7. Admin list: `/admin/payments`
- `backend/src/schemas/types/` new Payment type + `payments` query; register in `backend/src/schemas/typeDefs.ts`.
- Resolver in a new `backend/src/resolvers/payments/` domain folder, wrapped with `createErrorHandler`, registered in `backend/src/resolvers/index.ts`.
- `backend/src/validation/shield.ts`: `payments` is ADMIN-only.
- `frontend/src/lib/graphql/queries/` new payment query + types.
- `frontend/src/app/admin/payments/page.tsx`: read-only table (date, Supporter email, product, amount, status), newest first. `export const dynamic = 'force-dynamic'` if it uses `fetchGql`.
- `frontend/src/app/admin/AdminLayoutClient.tsx`: sidebar link.

### 8. `backend/src/services/stripe.ts`
Remove the stale `// TODO` comments.

### 9. Tests
- Backend unit/integration: signature rejection (missing + invalid), each event handler, idempotency (replay → one Payment, one Discord call, one email), coffee vs meeting email branching, `payments` query auth (ADMIN allowed; USER, EDITOR, anonymous denied). Stripe, Resend and Discord mocked.
- Frontend: admin payments list renders rows and empty state.

## Manual Deploy Steps (Luis)

1. **nginx:** add `location /webhooks/` proxying to the backend in `server/nginx/default.conf` (today only `/graphql` and `/health` are proxied).
2. **Stripe dashboard:** create the webhook endpoint `https://luisfaria.dev/webhooks/stripe` for the 4 events; set `STRIPE_WEBHOOK_SECRET` on the droplet.
3. **Email forwarding:** the root domain has no MX, so nothing receives mail at `contact@`. Set up free forwarding (e.g. ImprovMX: two MX records + SPF at GoDaddy) to Luis's personal Gmail. Check the SPF record includes both Resend and the forwarder. Send a test email to `contact@luisfaria.dev`.
4. **Local dev:** `stripe listen --forward-to localhost:4000/webhooks/stripe` and use the printed `whsec_` as `STRIPE_WEBHOOK_SECRET`.
