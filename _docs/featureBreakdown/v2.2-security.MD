# Security Authentication

## v2.2.0 🔥 | `feature/secure-authentication`

On this version, we will implement the most secure way to authenticate users and store their credentials allowing to access login area and admin area (if role == 'ADMIN').

## Current problems (4 issues)

---

### 1. JWT in `localStorage` + JS-readable cookie

- Token is stored in:
  - `localStorage` (accessible to any JS running on the page, including XSS payloads).
  - A cookie created with `js-cookie` (also readable by JS).
- **Impact:**
  - Any XSS → attacker can steal the JWT → full account takeover.
  - You also duplicate storage (more attack surface, more complexity).

**Core rule:** long‑lived auth tokens should never be readable by JS.

---

### 2. Mixed cookie + header auth = CSRF / confusion risk

- Apollo sends:
  - `Authorization: Bearer <token>` header from `localStorage`, AND
  - cookies (`credentials: 'include'`).
- Middleware accepts:
  - Either cookie token or header token.

**Risks:**

- If backend at any point trusts the **cookie** alone for auth, you are open to **CSRF**:
  - Malicious site → user’s browser auto-sends cookie → state-changing GraphQL mutation succeeds.
- Ambiguous source of truth:
  - Harder to reason about which credential is authoritative.
  - More places to misconfigure security on the backend.

---

### 3. Client-side role checks are not trustworthy

- `isAdmin()` reads `localStorage` token and decides if user is admin.
- Middleware also decodes token, but any **client-side** check must be treated as **UX only**.
- If any admin-only behavior depends solely on frontend checks, it’s bypassable.

---

### 4. Token lifecycle / revocation

- Token is just persisted for 7 days (`expires: 7` on cookie).
- No rotation / refresh flow.
- Logout only removes from localStorage and deletes the cookie via JS; if server is compromised or misconfigured, there's no server-side invalidation.

---

## Solution (for a more secure frontend auth)

Pragmatic hardening path that doesn't fight Next.js/Apollo:

---

### 1. Move fully to **httpOnly, secure cookies** for the token

- **Backend responsibility:**
  - On successful login/register, set a JWT in a **httpOnly, `secure`, `sameSite=strict|lax` cookie**.
  - Do **not** return the token to the client, or if you must, do not store it in localStorage.
- **Frontend responsibility:**
  - Stop using `localStorage` for the auth token entirely.
  - Authenticated requests just rely on `credentials: 'include'` + cookie.

Concretely for frontend:

- In `AuthContext`:
  - Remove all `localStorage` reads/writes for `token`.
  - Do **not** keep `token` in React state; keep only `user`.
- In Apollo `authLink`:
  - Remove the `localStorage.getItem('token')` logic and `authorization` header.
  - Rely solely on cookies (`credentials: 'include'` is already set).

---

### 2. Derive `user` from backend, not from stored token

Options:

- **Preferred:** have a `me` GraphQL query that returns current user based on cookie.
  - On `AuthProvider` mount:
    - Call `me` query (or use Suspense/Server Component patterns if you want).
    - Set `user` in context.
- **Temporary:** if backend still returns token + user on login/register:
  - Use the **returned user object only**; ignore/throw away the token on the client side.
  - Still rely on cookie for actual auth.

This way, even if an attacker steals JS-exposed state, they can’t get the raw credential.

---

### 3. CSRF protection

If you use cookies for auth:

- Ensure backend:
  - Uses `sameSite=strict` (or at least `lax`) for auth cookie.
  - For sensitive mutations, consider a **CSRF token**:
    - Backend sets a separate non-httpOnly CSRF cookie.
    - Frontend reads it and sends a `X-CSRF-Token` header.
    - Backend verifies header vs cookie.

Frontend side:

- Add CSRF header in Apollo link once backend supports it.
- Continue with `credentials: 'include'`.

---

### 4. Role checks and admin protection

- Keep **all real authorization** on the backend and middleware.
- Frontend:
  - Can still use `isAdmin()` **based on `user.role` from context**, not decoding the token from storage.
- Middleware:
  - Continue to read token from **httpOnly cookie** (Next middleware can read it).
  - Use that to guard `/admin` routes.
- Remove `isAdmin.ts` usages that rely on reading token from `localStorage`.

---

## Change plan (frontend)

---

**Phase 1 – Stop storing JWT insecurely**

- **`src/lib/auth/AuthContext.tsx`**
  - Remove:
    - `localStorage.setItem('token', ...)`
    - `localStorage.getItem('token')`
    - `localStorage.removeItem('token')`
    - Any token usage in state (`token`, `setToken`), and `isAuthenticated: !!token`.
  - Keep `user` only, and maybe `isAuthenticated: !!user`.
  - On startup:
    - Instead of reading from storage, eventually fetch `me` from backend.

- **`src/lib/apollo/client.ts`**
  - Remove the `authLink` that reads from `localStorage` and sets `authorization` header.
  - Keep `httpLink` with `credentials: 'include'`.

- **`src/lib/auth/isAdmin.ts`**
  - Replace this with a simple function that checks `user.role` from `useAuth`, or remove and inline checks in components.
  - Never decode JWT on the client for security decisions.

---

**Phase 2 – User bootstrap & logout flow**

- Implement a `me` query in backend (if not already).
- Add a hook / effect in `AuthProvider` to:
  - Call `me` on mount.
  - Set `user` or `null`.
- `logout` should:
  - Call a backend `logout` mutation or endpoint that clears the **httpOnly cookie**.
  - Then clear `user` in context and redirect.
